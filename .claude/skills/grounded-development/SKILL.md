# Grounded Development

근거 없이 구현하지 않는다. 구현 전에 **무엇을, 왜, 어떤 제약에서, 어떻게 확인할지**가 말로 정리되어 있어야 한다.

이 스킬은 다섯 개의 관문(Gate)으로 이루어진다. 순서대로 통과하되, 이미 충족된 관문은 "충족됨: <근거>" 한 줄로 넘어간다.

```
G1 요구사항 정의 → G2 흐름 이해 확인 → G3 1차원 답변 점검 → G4 근거 장부 → G5 검증 기준 → 구현 → 증거로 완료 보고
```

## 공통 규칙

- **보고 나서 묻는다.** 코드·문서·설정·이력에서 확인할 수 있는 것은 직접 확인하고, 사용자만 답할 수 있는 것만 묻는다.
- **한 번에 하나만 묻는다.** 가장 큰 미결 사항 하나를 묻고 멈춘다. 답이 구현을 바꾸지 않는 질문은 하지 않는다.
- **사용자의 답과 AI의 예시를 구분한다.** AI가 제안한 내용을 사용자가 동의한 사실로 기록하지 않는다. 기록할 때는 `[사용자]`, `[AI 제안]`, `[확인됨: 출처]`로 표시한다.
- **추측을 사실처럼 말하지 않는다.** "아마", "보통은", "~일 것이다"가 나오면 그 문장은 가정(Assumption)으로 옮긴다.

## G1. 요구사항 정의

구현 전에 아래 항목을 채운다. 비어 있는 항목 중 결과물을 바꾸는 것부터 하나씩 묻는다.

| 항목 | 질문 예 |
|---|---|
| 목표 | 이게 완성되면 누가 무엇을 할 수 있게 되나요? |
| 사용자·규모 | 사용자는 누구고, 얼마나 많나요? (요청량, 데이터 크기) |
| 제약 | 운영 시간, 예산, 기존 스택, 마감, 팀 역량 중 무엇이 고정인가요? |
| 비목표 | 이번에 하지 않을 것은 무엇인가요? |
| 성공 기준 | 무엇을 보면 "됐다"고 판단하나요? (관찰 가능한 형태로) |

요청이 여러 해석으로 갈리면 해석을 나열하고 어느 쪽인지 묻는다. 조용히 하나를 고르지 않는다.

## G2. 흐름 이해 확인

사용자가 질문하거나 설계를 승인하려 할 때, 그 질문·승인이 **흐름을 이해한 상태에서 나온 것인지** 확인한다. 답을 주기 전에 다음 중 하나를 요청한다.

- **재진술:** "이 요청이 들어와서 응답이 나갈 때까지 어떤 단계를 거치는지 직접 설명해 주세요."
- **예측:** "X가 실패하면 사용자에게 어떤 일이 생길까요?"
- **경계:** "이 설계에서 가장 먼저 바꾸게 될 부분은 어디라고 보나요?"

판정:
- 사용자의 설명이 단계를 빠뜨리거나 원인과 결과가 뒤바뀌어 있으면 **정답을 바로 주지 않는다.** 빠진 지점을 가리키는 더 좁은 질문이나 힌트를 준다.
- 설명이 흐름을 맞게 짚으면 "충족됨"으로 기록하고 진행한다.
- 사용자가 "그냥 알려줘"라고 하면 답을 주되, 확인되지 않은 이해를 전제로 진행한다는 점을 한 줄로 남긴다.

## G3. 1차원 답변 점검

사용자의 답(또는 AI 자신의 답)이 **한 가지 요인만으로 결론을 낸 것**인지 점검한다. 신호:

- 근거가 하나뿐이다. ("확장성이 좋아서", "요즘 다 이걸 써서", "AI가 추천해서")
- 비용·제약·대안이 언급되지 않는다.
- 실패하는 상황이나 운영 부담이 빠져 있다.
- 규모·시간 같은 숫자 조건과 결론이 연결되지 않는다.

신호가 보이면 다음 축 중 빠진 것 하나를 골라 묻는다.

- **제약:** "주어진 조건(예: 주당 운영 1시간)에서도 이 선택이 맞나요?"
- **비용:** "이걸 택하면 무엇을 포기하거나 추가로 떠안나요?"
- **대안:** "더 단순한 방법은 무엇이고, 왜 그걸 버렸나요?"
- **실패:** "이 부분이 멈추면 무엇이 깨지나요?"
- **변화:** "조건 X가 10배가 되면 결론이 바뀌나요?"

AI 자신의 제안에도 같은 점검을 적용한다. 단일 근거로 복잡한 구조를 권하고 있다면 스스로 더 단순한 안을 먼저 제시한다.

## G4. 근거 장부

구현할 각 결정마다 근거를 연결한다. 근거가 없는 결정은 구현하지 않는다.

```markdown
| 결정 | 근거 (요구사항/제약/증거) | 출처 | 가정 여부 |
|---|---|---|---|
| 단일 서버 + SQLite | 독자 100명/일, 운영 주 1시간 | [사용자] | 아님 |
| 캐시 미도입 | 측정된 병목 없음 | [확인됨: 부하 테스트 결과] | 아님 |
| 이미지 업로드 제외 | 비목표로 합의 | [사용자] | 아님 |
| 백업은 일 1회로 충분 | 데이터 손실 허용 범위 미확인 | [AI 제안] | **가정 → 확인 필요** |
```

- **가정** 행이 결과를 바꿀 수 있으면, 구현 전에 그 가정을 질문으로 바꿔 묻는다.
- 요청하지 않은 기능·추상화·설정은 장부에 근거가 없으므로 넣지 않는다.

## G5. 검증 기준

코드를 쓰기 전에 "됐다"를 판단할 방법을 먼저 정한다.

- 각 성공 기준을 **실행할 수 있는 확인 방법**으로 바꾼다. (테스트, 명령, 재현 절차, 측정값)
- 버그 수정은 먼저 실패를 재현하는 방법을 정한다.

완료를 보고할 때는:
1. 확인 방법을 **지금** 실행한다.
2. 출력 전체를 읽는다. (종료 코드, 실패 수, 경고)
3. 결과가 주장을 뒷받침할 때만 "완료"라고 말한다. 출력의 핵심 줄을 함께 보여준다.
4. 실행하지 못한 확인이 있으면 "미검증"으로 명시한다. "될 것 같다", "아마 통과" 같은 표현으로 완료를 대신하지 않는다.

## 생략 조건

- 오타, 이름 변경, 원인이 명백한 한 줄 수정 → G1~G3 생략, G5만 적용.
- 사용자가 "확인 없이 진행"을 명시 → 가정 목록을 한 번에 보여주고 진행하되, 장부와 검증은 유지.
- 이 스킬과 프로젝트의 CLAUDE.md/AGENTS.md가 충돌하면 프로젝트 규칙을 따른다.
